## 1. What M0 measures and how

The bandwidth that one channel (one DDR4 bank, 64 B × 300 MHz = 19.2 GB/s per direction at the
AXI port) and all four channels together deliver to a kernel clocked like the Tesseract core, for
reads, writes and both at once, over transfer sizes, burst lengths, the number of bursts in
flight and the number of AXI IDs. The kernel counts cycles itself (from the cycle its first request
can be generated to its last response, per channel and direction), so launch overheads (XRT, PCIe)
are not in the number;
the host tool also reports the wall-clock rate. Every run is checked: read data by a checksum,
written data by reading it back, status and error responses. The bandwidth kernel uses the same
AXI bridge as the Tesseract kernels (`tsr_xrt_axi_bridge`: 2 register slices per AXI channel,
AxCACHE 0011, 4-bit IDs, `ap_clk` 300 MHz, the same `sp=` bank binding as `hw/u200/k4.cfg`) and,
in its default packaging, the same `m_axi` interconnect hints (MAX_BURST_LENGTH 64,
NUM_READ_OUTSTANDING 16, NUM_WRITE_OUTSTANDING 32: the `component.xml` bus parameters the `v++`
linker sizes the kernel-side interconnect with; `lint.sh` checks that the two packagers agree), so
it sees the memory the way the core will. The engine itself can keep 64 bursts in flight per
direction: the outstanding sweep above 16 reads / 32 writes then shows what the core's
interconnect allows. A second packaging with 64 / 64 hints (`wide`, §4) is for comparison only;
every M0 number records which xclbin it came from.

## 2. Kernel interface and register map

Vitis RTL kernel `tsr_bw_k4` (module name = kernel name), `ap_ctrl_hs`, `ap_clk` (300 MHz),
`ap_rst_n` (active low, synchronous), `interrupt`; `s_axi_control` AXI4-Lite, 32-bit data, 12-bit
address (range 0x1000); `m_axi_ch0..3` AXI4, 512-bit data, 64-bit address, 4-bit ID (the signal
list of the Tesseract kernels). Parameters of the packaged top: `NUM_CH` 4, `ADDR_BEAT_W` 28 (16 GiB
per channel), `AXI_SLICES` 2, `CTRL_PIPE` 2.

`s_axi_control` (byte offsets; decoded on bits [11:2]; unmapped offsets read 0 and ignore writes;
every response OKAY; RW registers honour WSTRB):

| Offset | Name | Access | Content |
|---|---|---|---|
| 0x000 | AP_CTRL | | as the Tesseract kernels (docs/platform-u200.md §2–§3): bit0 ap_start (a write of 1 sets it; cleared when the start is accepted, ap_idle drops in the same edge), bit1 ap_done (COR), bit2 ap_idle, bit3 ap_ready (COR), bit7 auto_restart (not supported) |
| 0x004 / 0x008 / 0x00C | GIE / IER / ISR | RW / RW / R, toggle on write | interrupt = GIE & IER[0] & ISR[0]; ISR[0] set at completion while IER[0] = 1 |
| 0x010 | `seed` | RW, arg | pattern seed (all channels) |
| 0x014 .. 0x01C | — | reserved | |
| 0x020 + 0x20 c | `ctrl<c>` | RW, arg | bit0 enable, bit1 read, bit2 write, [14:8] burst beats B (1..64), [22:16] outstanding bursts per direction (1..64), [26:24] id_log2 (0..4); other bits ignored |
| +0x08 / +0x10 / +0x18 | `bytes<c>`, `rd_off<c>`, `wr_off<c>` | RW, arg (u64) | bytes per direction; byte offsets of the read and the write region in the channel's buffer |
| 0x0A0 + 8 c | `ch<c>` | RW, arg (u64, `void*` on `m_axi_ch<c>`) | device address of the buffer bound to channel c (XRT: the buffer object's address) |
| 0x0F0 | BW_VERSION | R | `{16'h4257 ("BW"), 8'h01, 8'(NUM_CH)}` = 0x42570104 |
| 0x0F4 | BW_INFO | R | `{16'd0, 8'(ADDR_BEAT_W), 8'(AXI_SLICES)}` = 0x00001C02 |
| 0x0F8 / 0x0FC | TOTAL_CYCLES | R (u64) | cycles from the accepted start to ap_done |
| 0x100 + 0x40 c | result block of channel c | R | below; cleared at every start, final at ap_done (read through registered paths: register read 3 cycles slower) |

Result block (offsets inside the block):

| Offset | Name | Content |
|---|---|---|
| +0x00 | STATUS | bit0 RAN (enabled, configuration valid), bit1 CFG_ERR (enabled, configuration refused: no traffic), bit2 RRESP (≥ 1 R beat with RRESP ≠ OKAY), bit3 BRESP (≥ 1 B with BRESP ≠ OKAY), bit4 UNEXPECTED (a response without an outstanding request was dropped by the bridge; also set by one arriving between runs), bit5 DONE (the channel finished this run) |
| +0x04 | ERRS | [15:0] R beats with RRESP ≠ OKAY, [31:16] B with BRESP ≠ OKAY (saturating) |
| +0x08 / +0x10 | RD_CYCLES / WR_CYCLES (u64) | cycles from go to the last R beat / the last B (§3); 0 without reads / writes |
| +0x18 / +0x20 | RD_BYTES / WR_BYTES (u64) | R beats received × 64 / W beats sent × 64 |
| +0x28 | CHECKSUM (u64) | read checksum (§3) |
| +0x30 / +0x34 | RD_LAT / WR_LAT | cycles from go to the first R beat / the first B |
| +0x38 / +0x3C | RD_BURSTS / WR_BURSTS | completed read bursts (last beats) / B responses |

Kernel arguments (`kernel_bw_k4.xml`, ids in this order; XRT writes every one before each start):
`seed` (0), then per channel `ctrl<c>`, `bytes<c>`, `rd_off<c>`, `wr_off<c>` (1 .. 16), then `ch0`
.. `ch3` (17 .. 20). The result registers are not arguments; the tool reads them with
`xrt::kernel::read_register` (exclusive compute-unit access, as the transport, docs/xrt-host.md §4.1).

## 3. Behaviour

- **Start**: ap_start while idle is accepted in the next cycle (ap_start := 0, ap_idle := 0 in
  the same edge, as `tsr_xrt_ctrl`); all arguments are latched (a snapshot: later register writes
  do not affect the run); a toggle goes to the four engines through `CTRL_PIPE` register stages.
  Each engine latches its configuration, checks it (3 cycles), and starts generating at **go**.
  Completion: when every engine has returned the toggle → ap_done, ap_ready, ap_idle, ISR.
  ap_start written during a run stays pending (as the adapter). Disabled channels finish at once.
- **Configuration check** (enabled channels; failure → CFG_ERR, no traffic, the other channels
  run normally): mode (read / write bits) not 0, B and outstanding in 1..64, id_log2 ≤ 4, buffer
  address 4 KiB aligned, `bytes` and the offset of every enabled direction multiples of 64, every
  enabled region ending at most at 2^(ADDR_BEAT_W + 6) bytes (16 GiB). The kernel does not know the
  buffer size: regions must lie inside the buffer (the tool ensures it). `bytes` = 0 is a valid
  empty run (no traffic, status RAN), also with an offset exactly at the limit (an empty region
  ending there); an offset beyond the limit is refused. (Review finding, fixed: with `bytes` = 0
  and the offset at 2^(ADDR_BEAT_W + 6), the region's start beat wrapped to 0 and the generators
  walked all 2^ADDR_BEAT_W beats of the buffer — 16 GiB of reads and pattern writes.)
- **Burst sequence** (per direction; the same rule for AR, AW and the W beats): from the region's
  first beat a, length = min(B, beats to the next 4 KiB boundary, beats left), a += length. No
  burst crosses 4 KiB; with an unaligned region start or B not dividing 64 some bursts are shorter
  than B; the region is covered exactly once. `tsr_bw_regs.h` `burst_len` / `burst_count` are the
  reference. Requests go out at up to one burst per cycle per direction.
- **IDs**: burst k of a direction uses AXI ID k mod 2^id_log2 (read and write sequences counted
  separately). R beats of different IDs may interleave; the engine does not care (counts per beat,
  completion per RLAST, an order-independent checksum).
- **Outstanding**: a burst counts from its generation to its last R beat (its B); at most
  `outstanding` per direction, so at most that many are in flight at the AXI port.
- **Write data**: W beats in burst order; the W beats of burst k start only after AW k was
  generated (W may still reach the AXI port before AW k is accepted, as AXI allows). 64-bit word
  at byte offset o of the buffer (8-aligned; the offset from the buffer address, not the device
  address) = `mix64(o ^ salt)`, salt = `seed << 32 | channel`, `mix64` = one xorshift64 step
  (`x ^= x << 13; x ^= x >> 7; x ^= x << 17`). It is invertible and linear over GF(2), so the
  hardware computes one `mix64` per beat and XORs constants: word i of the beat at o is
  `mix64(o) ^ mix64(8i) ^ mix64(salt)`. Every word encodes its own location, channel and seed: a
  write that is missing (stale data of another seed), misplaced, duplicated or bit-corrupted shows
  up as a mismatch.
- **Read checksum**: Σ over the received beats of Σ_i rotl64(w_i, 8 i) (mod 2^64), words in
  little-endian byte order. Independent of the arrival order of beats, sensitive to every bit, to
  the word position in a beat and to a duplicated or missing beat.
- **Cycles**: the engine's counter is 1 in the first cycle of go and counts every cycle; RD_CYCLES
  / WR_CYCLES are its value in the cycle the engine sees the last R beat / B, RD_LAT / WR_LAT in
  the cycle of the first. The engine sees responses after the bridge's response slices: with a
  memory that answers in the cycle after the request (the bench's ideal regime) the first R beat
  reaches the engine `2 × AXI_SLICES + 4` cycles after go (8 at `AXI_SLICES` 2, §5.2), so a
  transfer of N beats at full rate takes N + 7 (reads) / N + 8 (writes) cycles. Bandwidth = bytes /
  (cycles / f_ap_clk).
- **Errors**: R / B responses with RRESP / BRESP ≠ OKAY are counted (ERRS) and flagged (STATUS);
  a response without an outstanding request is dropped by the bridge's ID filter and flagged
  (UNEXPECTED). There is no abort: a run that never completes (a stuck interconnect) needs a card
  reset (`xbutil reset`); the tool says so on its timeout.
- **Reset**: `ap_rst_n` low for ≥ 3 cycles (the AXI-side bound of docs/platform-u200.md §5; this
  kernel has no core and no `RST_PIPE`, so the 4-cycle minimum of the Tesseract kernels does not
  apply; the bench's `reset` test uses 3, 4 and 20): every register, argument and result back to 0,
  no AXI traffic.

## 4. Implementation, packaging, build

**RTL**: `tsr_bw_kernel` = `tsr_xrt_reset` (the adapter's; per channel 13 equal reset copies: 12
for the parts of the bridge, one for the engine and its toggles; docs/platform-u200.md §8.3) +
`tsr_bw_ctrl` + per channel `tsr_bw_engine` → `tsr_xrt_axi_bridge`
(the adapter's: base add, `AXI_SLICES` register slices per AXI channel, ID filter, error events).
Everything between the control block and an engine is registered on both sides (toggles through
`CTRL_PIPE` stages, a static configuration snapshot, a registered result path), so each channel can
sit in the SLR of its bank. The generators walk the burst sequence with the beat address split in
block index and offset inside the 4 KiB block and a down-counter of blocks to the region end, so
the one-burst-per-cycle loop has no wide subtract. The checksum is a registered 8 → 4 → 2 → 1 adder
tree plus the accumulator; the pattern is one registered `mix64` per beat and an XOR.
`filelist.f` is complete (tsr_pkg, `tsr_rslice` from rtl/core/tsr_mem_arb.sv, the three adapter
files, the kernel); no technology wrapper is involved.

**Generated files**: `gen_bw.py` writes `tsr_bw_k4.v`, `kernel_bw_k4.xml` and the bench wrapper
`tb/platform/bw/sv/kwrap_tsr_bw_k4.sv` from one table (the AXI signal list comes from
`../gen_tops.py`); `gen_bw.py --check` (run by `lint.sh`) fails on a stale file.

**Packaging**: `rtl/platform/alveo_xrt/bw/package_bw_xo.tcl <repo> <outdir> [core|wide]` (the flow
of the adapter's `package_xo.tcl`: IP packager, Vitis kernel properties, FREQ_HZ 300 MHz, the m_axi
hints, the register map with the arguments, `ipx::check_integrity -kernel` / `-xrt`, `package_xo`,
the source manifest `tsr_bw_k4.sources.sha256`) → `build/u200/xo/tsr_bw_k4.xo`. Hints: `core`
(default) = the Tesseract kernels' MAX_BURST_LENGTH 64 / NUM_READ_OUTSTANDING 16 /
NUM_WRITE_OUTSTANDING 32 (the M0 baseline, §1); `wide` = 64 / 64 / 64 (the engine's maximum) →
`build/u200/xo/wide/tsr_bw_k4.xo`. Before this was split, the only packaging used 64 / 64, so M0
would have measured a differently sized interconnect than the core gets (review finding). Results:
§4.1.

**xclbin** (built 2026-10-24, §4.1): `hw/u200/bw/build_bw_xclbin.sh [hw|hw_emu]` (`TSR_BW_HINTS=core`
default, or `wide`) repackages the `.xo` when it is missing, packaged with other hints, or its
source manifest no longer matches the working tree (`sha256sum -c`), then `v++ --link --config
hw/u200/bw/bw.cfg` → `build/u200/bw/tsr_bw_k4.xclbin` (`build/u200/bw_wide/` for `wide`).
`bw.cfg`: `kernel_frequency=300`, one compute unit `tsr_bw`, `sp=tsr_bw.m_axi_ch<c>:DDR[c]` (the
binding of `tsr_u200_k4`), no `slr=` (the compute unit spans the banks' SLRs); `TSR_BW_FLOORPLAN=1`
adds the draft `bw_floorplan.tcl` (engine + bridge of channel c into the dynamic-region pblock of
DDR[c]'s SLR, with the bank SLRs of `platforminfo`, docs/platform-u200.md §8; not used for the
xclbin and not needed for timing, §4.1). With `PLATFORM_REPO_PATHS` unset the script uses the
extracted development platform under `build/platforms` (as `hw/u200/build_xclbin.sh`); without a
platform it stops with exit 3 and says what to install (tested). `TSR_VIVADO_LOCK` serialises
Vivado / v++ runs.

## 5. Verification

### 5.1 Bench (`tb/platform/bw`)

`bw_bench.cpp` (Verilator C++; class `Vbw` = `tsr_bw_kernel` with any parameters, or the packaged
`tsr_bw_k4` behind `kwrap_tsr_bw_k4.sv`), built and run by `run_bw.py`:

- **Host**: the adapter bench's XRT-like AXI4-Lite master (a copy of `tb/platform/kernel_dut.h`
  XrtHost, serial lanes: random VALID delays, early / late BREADY / RREADY, checks of the slave), writing the whole
  argument map 0x010 .. 0x0BC like XRT, GIE / IER, AP_CTRL = 1; completion by interrupt or by
  polling AP_CTRL every 16 cycles (random per run).
- **Memory**: the adapter's `fr::MemModel` (tb/fastreplay/memmodel.h) behind an AXI4 translation,
  as `kernel_dut.h` does it; the 16 AXI IDs are mapped onto the model's 8 read / 4 write ids (stricter
  than AXI: order kept within each group, interleaving across groups). Regimes: `ideal` (latency 0,
  every READY / VALID 1), `fast`, `rand`, `slow`, `ordered`. Random 4 KiB aligned buffer
  addresses up to near 2^64. Optional SLVERR / DECERR and stale responses.
- **Checks**: the adapter bench's AXI4 checks (VALID / payload held, SIZE 6, INCR, CACHE 0011,
  PROT / LOCK / QOS 0, aligned, inside the buffer, LEN ≤ 63, no 4 KiB crossing, WSTRB all ones,
  WLAST, nothing during / right after reset) plus: every AR / AW equals the next burst of the
  reference sequence (address, length, ID), in-flight bursts ≤ outstanding, no traffic on a disabled
  or refused channel; per run every result register against the reference (status, errors ==
  injected, bytes, bursts, checksum over the bytes the model held, cycles ≥ beats, latency ≤ cycles
  ≤ TOTAL_CYCLES), the written region bit-exact and complete, nothing written outside it, nothing
  read outside the read region, AP_CTRL / ISR / interrupt after the run, quiescence at completion,
  no RTL assertion. In the ideal regime with 64 outstanding, exact streaming: RD_CYCLES = RD_LAT +
  beats − 1 and WR_CYCLES = WR_LAT + beats − first burst, and cycles − beats ≤ 4 + 4·AXI_SLICES.
- **Tests** (`--test`): `regmap`, `single` (each channel alone, R / W / RW, 4 burst / outstanding
  / ID settings), `all4` (same and mixed modes), `combos` (bursts {1,2,3,7,16,31,32,33,63,64} ×
  outstanding {1,2,3,5,16,63,64}, IDs 1..16, unaligned regions, 64 B .. 256 KiB, plus `--runs`
  random multi-channel runs), `ideal` (§5.2), `cfgerr` (17 invalid configurations, the legal
  limit, `bytes` = 0 with the offsets at the limit — read, write, both: legal and empty — and one
  just beyond it: refused), `errors` (SLVERR / DECERR, stale R / B), `apctrl` (back-to-back, result clearing, the
  snapshot also against a fast host rewriting the arguments right after AP_CTRL = 1, queued
  ap_start, no channel), `reset` (ap_rst_n 3 / 4 / 20 cycles in the middle of traffic), `big`
  (16 MiB read + write on all channels).

test, 16 MiB read + 16 MiB write on all four channels at once with 0–2 cycles of memory latency:

cycles (4096 beats in 4544 cycles), a 1-beat read 8 cycles, a 1-beat write 9; full rate needs 2
bursts of 64 beats in flight (reads and writes), or 8 one-beat reads / 16 one-beat writes. These are
the kernel's own limits; the card's numbers come from M0 (§7).

### 5.3 Mutation campaign (`tb/platform/bw/mutate_bw.py`)

Every mutant is one textual change of `tsr_bw_engine.sv` (43) or `tsr_bw_ctrl.sv` (12) in a
scratch copy, built with `-Wno-fatal` and run through regmap, single, all4, combos (15 random runs),
ideal, cfgerr, errors, apctrl and reset in the ideal, rand and slow regimes, stopping at the first
failure (`--stop-on-fail`). The unmutated copy passes. Final run (2026-10-23, final RTL and bench,
default build): **55 mutants, 52 killed, 3 survived, all 3 equivalent**; 432 s of builds and runs.
Re-run after the review fix (`bytes` = 0 at the limit) with two new mutants (`E_rend_bytes0`,
`E_wend_bytes0`: the fix undone for reads / writes): **57 mutants, 54 killed**, the same 3
equivalent survivors; 495 s.

Survivors, all equivalent:
- `E_w_no_ahead` (W beats may start before their AW was generated): legal AXI4 (a slave may receive
  W before AW), the memory model accepts it, the beats and bursts are the same. Predicted equivalent.
- `C_snapshot_live` (the engines take the live argument registers instead of the snapshot): they
  latch them `CTRL_PIPE` + 1 cycles after the accept, before the AXI4-Lite slave can complete another
  write at `CTRL_PIPE` 2. Predicted; with `CTRL_PIPE` 4 the race test of `apctrl` (a fast host
  rewriting the arguments right after AP_CTRL = 1) kills it ("700 of 700 beats not written with the
  snapshot").
- `E_cs_nodrain` (the channel reports done before the checksum pipeline has drained): the pipeline
  drains 3 cycles after the last beat, while the completion needs the toggle stages, ap_done and an
  AXI4-Lite read before the host can read the checksum. Expected to be killed, found equivalent on
  analysis; the drain stays (correct by construction, 3 registers of state).

## 6. Host tool `tsr_bw` (`sw/tools/tsr_bw.cpp`)

```
cmake -S . -B <build> -DTSR_WITH_XRT=ON [-DTSR_XRT_ROOT=...]   # docs/xrt-host.md §7
cmake --build <build> --target tsr_bw
TSR_XCLBIN=build/u200/bw/tsr_bw_k4.xclbin <build>/bin/tsr_bw [options]
```

|---|---|---|
| `--xclbin F` / `--device N\|BDF` / `--kernel K` | `$TSR_XCLBIN` / `$TSR_XRT_DEVICE` or 0 / `tsr_bw_k4` | |
| `--sizes LIST` | `1M,16M,256M,1G` | bytes per channel and direction |
| `--bursts LIST` | `1,4,16,64` | burst length in beats |
| `--outstanding N` / `--ids N` | 32 / 1 | bursts in flight per direction / AXI IDs (1, 2, 4, 8, 16) |

| `--pcie` | off | host ↔ card DMA rate per channel (`xrt::bo` write / read of 256 MiB, wall clock) |

Flow: device and xclbin (kernel lookup, one compute unit, ap_ctrl_hs, control range ≥ 0x1000,
every argument by name with the offset and size of `tsr_bw_regs.h`, BW_VERSION, the DATA clock of
the clock topology; AP_CTRL read until idle, which consumes a completion an earlier process did not
wait for — accepting a start does not clear ap_done and `xrt::run` would otherwise complete the
first run at once, the transport's issue of docs/xrt-host.md §3; after every run AP_CTRL must be
idle again, else the completion was stale and the tool waits for the run), one device-only buffer
per channel; **self-check** per channel (4 MiB of host
random data read by the kernel → checksum; a 4 MiB kernel write read back by the host → pattern);
optional PCIe rates; **fill**: the kernel writes the pattern of a fill seed over the read region of
every channel (largest size), the host computes the reference checksum of every size prefix; then
for every mode × size × burst: each listed channel alone and all channels together, `--reps` runs,
each checked (status = DONE | RAN, no error responses, bytes and burst counts, read checksum,
cycles ≥ beats, written region verified). Output per point: mode, channels, size, burst,
outstanding, aggregate read / write / sum GB/s by the kernel's cycles, % of 64 B per cycle per
direction, wall-clock GB/s, first-beat latencies, ok / FAIL with the findings. Exit status 0 = all
checks passed, 1 = a check failed, 2 = setup error.

Verified without a card (2026-10-23, XRT 2.18.179 unpacked, `-DTSR_WITH_XRT=ON -DTSR_WITH_LLAMA=OFF`):
compiles and links with `-Wall -Wextra` warning-free; `--mock` (sizes 64K / 1M / 8M, bursts 1 / 16 /
64, 2 repetitions, PCIe, outstanding sweep): 387 runs, 0 failed; each injected mock fault (wrong
checksum, one corrupted written word, a BRESP error, a short read) makes the affected runs fail and
the tool exit 1; `tb/platform/bw/noop/noop_smoke.sh` on XRT's no-op shim with metadata-only xclbins:
`--dry-run` opens the device, reads the DATA clock (287 MHz in the test xclbin, `--clock-mhz`
override), allocates a buffer per bank, sets every argument (XRT checks the sizes) and completes
`xrt::run` start / wait; a wrong argument offset, a wrong size, a missing argument, a 0x800 control
range, two compute units, an unknown kernel and a buffer larger than its bank are refused with the
reason; the no-op xclbin's argument table equals `kernel_bw_k4.xml` (12 checks, all pass). Not
run: anything on a card (register reads, DMA, real runs and their numbers).

## 8. Open items

- Nothing ran on hardware, and this kernel has no hw_emu run. The xclbin is built (§4.1): without a
  floorplan the placer put all four engines and bridges in SLR1 and met 300 MHz, so
  `bw_floorplan.tcl` is not used and not needed for timing.
- Timing (§4.1): the first link had +0.025 ns on the kernel clock, on the R slice's clock-enable
  fan-out in `tsr_rslice`, which every Tesseract bridge shares. Changed since (docs/platform-u200.md
  §8.3: the payload registers of the always-ready R / B chains have no clock enable now; out of
  context the worst bridge payload-enable path went from +0.286 ns, this path, to +0.569 ns, from an
  AXI READY input; WNS +0.278 ns on a control-to-engine path), and the relinked xclbin has +0.055 ns
  on the kernel clock (shell logic) and +0.110 ns on the kernel's own worst path (a W slice's
  `rdy_q` → `main_q` S pin, fan-out 283). If a rebuild misses 300 MHz in a generator, the loop can
  be shortened without changing behaviour: the 4 KiB carry of a burst is `~z & (lo ≥ 64 − B)`
  (registered threshold) and the next offset is then 0, else `lo + B` or the region end. If it
  misses on reset nets, the per-channel reset copies need protection from phys_opt's
  equivalent-driver rewiring (a vendor attribute, adapter / tech layer).
- The kernel cannot be aborted; a hung run needs `xbutil reset` (the tool's timeout message says so).
- `bw_bench.cpp` carries copies of the adapter bench's AXI4-Lite host and AXI4 checks
  (`tb/platform/kernel_dut.h` is the adapter's file and is tied to the trace replayer); a shared
  header would remove the duplication.
- The tool's no-hardware checks (`--mock`, `noop_smoke.sh`) run from `tb/platform/bw/test_bw.py`
  only when a `tsr_bw` binary exists; they are not ctests of the XRT build yet.
- `tsr_bw` reads results with the deprecated `xrt::kernel::read_register` (exclusive CU), as the
  transport; on XRT versions that drop it, use `xrt::ip` without `xrt::run` (register-driven
  start, as the transport's `TSR_XRT_CTRL=regs`).
